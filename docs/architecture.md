## 2. Dify 调用流程

整个调用链路从 Dify Workflow 的触发开始，到用户获得可下载的 DOCX 文件结束：

Dify Workflow 被触发后，上游节点（LLM Agent、HTTP Request、Code 节点等）负责产出结构化的 JSON 数据。这些数据是业务逻辑的产物——可能是 LLM 根据用户对话提取的合同参数，也可能是 HTTP 节点从 ERP 系统拉取的结算明细。数据产出后，Workflow 中的 Tool 节点被激活，该节点配置为调用 `generate_docx` 接口。

Tool 节点将三个参数打包为 `multipart/form-data` 请求发送给 Skill 服务：`data` 是序列化后的 JSON 字符串，`title` 是期望的文件名，`template` 是 DOCX 模板文件的二进制内容。如果模板文件在 Dify 中以文件变量形式存在（例如用户上传或从知识库引用），则直接作为文件流传递。

Skill 服务处理完毕后，返回包含 `file_url` 的 JSON 响应。Dify Tool 节点将这个响应解析为结构化变量，供下游节点使用。下游可以是 Answer 节点（将下载链接以消息形式发送给用户）、HTTP 节点（将文件推送到 OSS / 企业网盘）、或 Code 节点（提取文件 URL 后进行后续处理）。

```
[Trigger] → [LLM/HTTP/Code] → [Tool: generate_docx] → [Answer/HTTP/Code] → [End]
   用户触发      产出 JSON         调用 Skill             处理输出文件
```

## 3. Skill 工作流程

Skill 服务内部的工作流程分为五个阶段，每个阶段都有明确的输入输出和错误处理边界：

### 3.1 请求接收与鉴权（API Layer）

FastAPI 接收 HTTP 请求后，首先进行鉴权校验。如果配置了 API Key，会校验 `Authorization` Header 中的 Bearer Token。鉴权通过后，解析 multipart 请求体，提取 `data`、`title`、`template` 三个字段。此阶段还会进行基础的参数校验：`data` 是否为非空字符串、`title` 是否符合命名规范（长度限制、非法字符过滤）、`template` 的 Content-Type 是否为 DOCX 格式。

### 3.2 数据解析与校验（Validation & Parsing）

将 `data` 字段从 JSON 字符串反序列化为 Python 字典。如果 JSON 格式不合法，立即返回 `INVALID_JSON` 错误。解析成功后，对数据进行结构校验——这不是业务校验（Skill 不关心业务语义），而是类型校验：确保嵌套层级合理、数组元素为对象、字段值类型可被模板渲染（字符串、数字、布尔值、日期等）。

同时，DOCX 模板文件被加载到内存。服务会验证文件确实是一个合法的 `.docx`（本质是 ZIP 包含特定的 XML 结构），而非伪装的文件。如果模板损坏或格式不正确，返回 `INVALID_TEMPLATE` 错误。

### 3.3 模板渲染（Render Engine）

这是 Skill 的核心阶段。使用 docxtpl 库将 JSON 数据注入 DOCX 模板。docxtpl 基于 Jinja2 模板引擎，但专门针对 DOCX 的 XML 结构做了适配——它理解 Word 文档的段落、表格、Run（文本片段）等结构，能在正确的位置插入变量值而不破坏文档格式。

渲染过程包括：遍历模板中的所有段落和表格单元格，查找 `{{...}}` 占位符并替换为 JSON 中对应的值；处理 `{{#array}}...{{/array}}` 循环标记，为数组中的每个元素复制表格行并填充数据；评估 `{{#if condition}}...{{/if}}` 条件块，根据布尔值决定是否保留内容；处理 `{{%image}}` 图片标记，将 Base64 数据解码后插入到指定位置。

如果模板中存在 JSON 数据无法匹配的变量，渲染引擎会根据配置决定行为：严格模式下返回 `TEMPLATE_RENDER_ERROR` 错误并列出未匹配的变量；宽松模式下将未匹配的变量替换为空字符串并在响应的 `rendering_summary` 中记录。

### 3.4 文件存储（File Storage）

渲染完成后，docxtpl 产出一个 `python-docx` Document 对象。将其序列化为 `.docx` 字节流，以 `{timestamp}_{uuid}.docx` 的命名规则保存到文件存储中。存储后端可以是本地临时目录（适合单机部署）或 MinIO / 对象存储（适合集群部署）。保存成功后，生成一个可访问的下载 URL，该 URL 包含时效性签名以防未授权访问。

### 3.5 响应返回

组装 JSON 响应，包含 `success`、`file_url`、`file_name`、`file_size`、`generated_at` 以及 `rendering_summary` 统计信息。HTTP 200 返回给 Dify Tool 节点。

```
请求接收 → 鉴权 → 参数解析 → JSON 反序列化 → 模板加载 → 模板渲染 → 文件存储 → 响应返回
            │          │           │              │           │           │
            ▼          ▼           ▼              ▼           ▼           ▼
         401 错误   400 错误    400 错误       422 错误    500 错误    200 成功
```

## 4. 文件生命周期

生成的 DOCX 文件从创建到删除，经历以下阶段：

**创建阶段** — 模板渲染完成后，文件被写入存储后端。文件名格式为 `{YYYYMMDD_HHMMSS}_{8位UUID}.docx`，确保全局唯一且可按时间排序。文件创建时，系统记录元数据：原始 `title`、生成时间、文件大小、来源请求 ID、关联的模板哈希值。

**活跃阶段** — 文件创建后进入活跃期，通过 `file_url` 可被多次下载。Dify Workflow 通常在收到响应后立即下载或转发文件。活跃期内，每次下载都会被记录（时间、来源 IP），用于审计和访问控制。

**过期阶段** — 文件达到生存时间（TTL，默认 24 小时）后进入过期状态。此时 `file_url` 不再可访问，返回 410 Gone。文件仍物理存在于存储中，但被标记为待清理。TTL 可通过环境变量 `FILE_TTL_HOURS` 配置。

**清理阶段** — 后台定时任务（默认每小时执行一次）扫描过期文件并执行物理删除。清理操作记录日志，包含文件名、大小、创建时间、删除时间。清理任务采用软删除策略——先移除文件的可访问性，再在下一个周期执行物理删除，以防误删。

```
[渲染完成] → [写入存储] → [活跃可下载] → [TTL 过期] → [标记待清理] → [物理删除]
     0s          ~0.1s        0 ~ 24h         24h          24h ~ 25h       25h
```

### 文件存储后端选择

| 后端 | 适用场景 | 优势 | 注意事项 |
|------|---------|------|---------|
| 本地目录 | 单机部署、开发环境 | 实现简单、零依赖 | 不支持水平扩展、需自行管理磁盘空间 |
| MinIO | 内网集群部署 | S3 兼容、支持集群、自带管理界面 | 需额外部署 MinIO 服务 |
| 云对象存储（OSS / COS / S3） | 云上部署 | 高可用、自动扩容、CDN 加速 | 需配置云厂商 SDK 和访问密钥 |

## 5. 模板渲染逻辑

### 5.1 变量替换

模板中的 `{{variable_name}}` 占位符被替换为 JSON 数据中同名字段的值。替换发生在 Word 文档的 Run 级别——docxtpl 会正确处理变量跨越多个 Run 的情况（这在手动编辑的 Word 文档中很常见），确保变量名不会因为 Word 内部的 XML 分段而被截断。

嵌套对象通过点号语法访问：`{{company.name}}` 对应 JSON 中 `{"company": {"name": "..."}}`。如果字段值为 `null` 或不存在，根据渲染模式决定行为（严格模式报错，宽松模式替换为空字符串）。

### 5.2 表格循环

模板表格中的某一行被标记为循环行：该行的某个单元格中包含 `{{#items}}`，另一个单元格包含 `{{/items}}`。渲染时，docxtpl 会为 JSON 中 `items` 数组的每个元素复制这一行，并用数组元素的字段值填充。循环行内的变量使用相对路径：`{{name}}` 对应数组当前元素的 `name` 字段。

```
模板表格:                        JSON 数据:
┌──────────┬──────────┐         {
│ 项目名称  │ 金额      │           "items": [
│ {{name}} │ {{amount}}│             {"name": "服务费", "amount": "50000"},
│ {{#items}}│          │             {"name": "咨询费", "amount": "30000"}
│          │{{/items}} │           ]
└──────────┴──────────┘         }

渲染结果:
┌──────────┬──────────┐
│ 项目名称  │ 金额      │
│ 服务费    │ 50000    │
│ 咨询费    │ 30000    │
└──────────┴──────────┘
```

### 5.3 条件渲染

`{{#if condition}}` ... `{{/if}}` 标记的内容块，根据 `condition` 的布尔值决定是否保留。condition 可以是 JSON 中的布尔字段，也可以是简单表达式。条件渲染常用于：合同中的可选条款、结算单中的税费行（根据是否含税决定显示）、报告中的异常项标注。

### 5.4 图片插入

`{{%image_variable}}` 语法用于在模板中插入图片。JSON 数据中对应的字段值应为 Base64 编码的图片数据，或一个图片 URL（服务端会先下载再插入）。docxtpl 支持设置图片尺寸，可通过模板中的图片占位符大小自动适配，或通过 `{{%image_variable | size(400, 300)}}` 语法指定宽高（单位为像素）。

### 5.5 格式保留

模板渲染过程中，原始模板的所有格式信息都被完整保留：字体、字号、颜色、对齐方式、页眉页脚、水印、表格样式等。docxtpl 只替换文本内容和结构（如复制表格行），不修改任何样式属性。这意味着设计师可以用 Word / WPS 精心设计模板的外观，而 Skill 只负责往里面"灌数据"。

## 6. 错误处理策略

Skill 服务采用分层错误处理，确保每个故障点都有明确的错误码和可操作的错误信息：

| 阶段 | 错误码 | HTTP 状态码 | 含义 |
|------|--------|------------|------|
| 鉴权 | `UNAUTHORIZED` | 401 | API Key 缺失或无效 |
| 参数校验 | `MISSING_FIELD` | 400 | 必填参数缺失 |
| 参数校验 | `INVALID_JSON` | 400 | data 不是合法 JSON |
| 参数校验 | `INVALID_TEMPLATE` | 400 | 模板文件格式不正确 |
| 大小校验 | `FILE_TOO_LARGE` | 413 | 文件超过大小限制 |
| 渲染 | `TEMPLATE_RENDER_ERROR` | 422 | 变量未匹配 / 语法错误 |
| 内部 | `INTERNAL_ERROR` | 500 | 未预期的服务器错误 |
| 可用性 | `SERVICE_UNAVAILABLE` | 503 | 服务过载 / 维护中 |

所有错误响应都包含 `error.code`（机器可读）和 `error.message`（人类可读），部分错误包含 `error.details`（附加调试信息）。Dify Workflow 可以通过条件分支节点根据错误码进行不同的错误处理逻辑。
